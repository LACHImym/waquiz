## アプリの前提

- コミュニティ「WA」の一メンバー（らち）が個人で作っている、公式ではないアプリ
- 静的サイト（GitHub Pages）＋ Supabase。**自前のサーバーを持たない**

- この「サーバーを持たない」ことが、後述するセキュリティ問題すべての根っこ

## 2026-08 前半：UIの作り直し

### 「補足」という概念を廃止
コメントと補足の2本立てが分かりにくかったため、コメントに一本化。

### コメント欄は「コメントする」を押してから表示
常時開いていると画面が重く、書く気のない人には邪魔だったため。

### 他ユーザーのアイコン表示
`profiles` テーブルに無い人でも Misskey の公開API（`users/show`）から引く。
一度引いたら端末に7日キャッシュし、ついでに `profiles` にも書き戻す。
こうすると、誰か一人が見た時点で全員のためにデータが揃っていく。

### 新着コメントページ
受信／送信のタブ。5件ずつ＋「もっと見る」。
受信には返信、送信には編集・削除。

### ランキングをハンバーガーメニューへ
マイページに置いていた面白クイズランキングを撤去し、
「いいね／面白クイズ／難問」の3つをランキングページに集約。

### 落とし穴：`[hidden]` が効かなかった
`.btn { display: inline-flex }` がブラウザ標準の `[hidden]` 規則に勝っていた。
`[hidden] { display: none !important; }` を全体に追加して解決。

## 2026-08 後半：WA王決定戦

### 仕様
- 全251問・一発勝負・やり直しなし・途中でやめたらそこで終了
- 出題中は正誤を見せない
- 同じ正解数は同順位

### 難問ボーナスを入れなかった理由
「運の要素を2割ほど足したい」という要望から、正答率に応じたボーナスを検討。
モンテカルロで600〜800回試行して検証したところ、
**ボーナスが無くても「実力1位が優勝する確率は27%」**しかなかった。
運の主因は問題の引き（±1.3問）ではなく**4択の当てずっぽう（±4.4問）**。
すでに運ゲーだったので、ボーナスは足さず、同点は同順位とした。

### 発覚：イベントボーナスが動いていなかった
`points.decisionBattle: 100` は設定にあるだけで、どこからも使われていなかった。
計測して確認：アーカイブ／ストック／入門編は `answers` に記録が入りポイントが動くが、
WA王は `wao_answers` / `wao_entries` にしか書かず `answers` には1行も入らない。
`totalRanking()` に完走者への+100を追加して解消。

## ★ 事故1：途中離脱者の記録が消えた

### 症状
「途中まで解いた」と言っている人が、軒並み **0問正解** で記録されていた。

### 原因
解答の記録を**最後に一度だけ**書き込む設計だった。
`window.addEventListener('pagehide', ...)` で離脱時にまとめて送っていたが、

1. ページを閉じる瞬間の通信はブラウザに打ち切られる
2. `pagehide` は**スマホでアプリを切り替えただけでも発火する**。
   その時点で内部的に「終了済み」の印が付くため、戻ってきて最後まで解いても
   二度と保存されない

つまり「アプリを切り替えた人」は全員、記録が消えていた。

### 対応
`wao_answers` に解答が残っていた1名（いっさん）だけ、そこから
正解数・回答数を再構築して復旧。
安全のため「**解答記録のほうが多い人だけ**」を対象にし、点数が下がる人が
1人も出ないようにした。

### 未対応（次にやること）
**1問ごとに記録する方式へ変更する。** これをやらないと同じ事故が必ず再発する。
日々のクイズ（`flushAbandon`）も同じ作りなので、途中離脱者のポイントが
毎日静かに消えている。

## ★ 事故2：外部から問題と正解が読まれた

### 症状
WA王決定戦の期間中、**外部から問題を引っ張って対策された事例**があった。

### 原因
`js/config.js` の Supabase anon キーが公開リポジトリに入っており、
RLS が全テーブル `select using (true)`＝キーを知っていれば誰でも全件読める設定だった。
`schema.sql` にもその旨が明記されていた（内輪向けの割り切り）。

読めていたのは問題だけではない：

| テーブル | 内容 |
|---|---|
| wao_entries | **大会のランキング。開催中もリアルタイムで** |
| wao_answers | 誰がどの問題を正解／不正解したか |
| questions | 問題文・正解・解説 |
| answers | 誰がどの問題を間違えたか |
| logins | 誰がいつログインしたか |
| profiles | 全員のハンドル・表示名・アイコン |

### キーの作り直しでは直らない
アプリは静的サイトで、問題を画面に出すために**ブラウザ自身がキーを持つ**。
開発者ツールを開けば誰でも取り出せる。リポジトリを非公開にしても同じ。
**アプリとデータベースの間にサーバー役を挟むしかない。**

### 対応の段階
- **第1段階（済）**：アプリが読む必要のないテーブルを閉じた（`wao_answers` / `history`）
- **第2段階（Plan A・今回）**：正解をブラウザに送るのをやめ、採点をデータベース側で行う
- **第3段階（Plan B・未着手）**：Edge Function で本人確認してから応答する

---

## Plan A の設計

### 前提となる発見
問題の保存形式が `choices: [正解, 不正解1, 不正解2, 不正解3]` で、
**`choices[0]` が必ず正解**だった（`correct_index` は常に 0）。
つまり `correct_index` を隠しても、`choices` を見れば正解が分かってしまう。

そこで Plan A は3点セットになる：

1. **保存済みの選択肢をシャッフルする**（1回限りの移行SQL）
   これで `choices` から正解が読めなくなる
2. **`correct_index` と `explanation` の読み取り権限を外す**
   テーブルごと閉じるのではなく**列単位**で外すので、
   一覧・件数・ランキングなど大部分のコードはそのまま動く
3. **採点をデータベース側の関数で行う**
   ブラウザは「この問題で、この選択肢を選んだ」とだけ送る

### Plan A の限界（正直に）
呼び出し元が誰かを確認できないため、
「自分の作った問題を見る」機能は、他人のハンドルを指定すれば覗ける。
らちが問題の大半を作っているので、ここは実質的に残る。
**塞ぐには第3段階（本人確認）が必要。**

また、問題IDを集めてから採点関数を1問ずつ叩けば、時間をかければ答えは集められる。
**一発で251問ぶんの答えをダウンロードすることはできなくなる**、という改善。

## 判断の記録（なぜそうしたか）

| 決めたこと | 理由 |
|---|---|
| スタンプの傾きを日数から計算 | `Math.random()` だと開き直すたび角度が変わる |
| 難問ボーナスなし | 検証したら既に運ゲーだった。足す意味がなかった |
| ランキングを全員表示 | 上位しか見えないと下位に競争意識が生まれない、という仮説の検証 |
| 復旧は「点数が上がる人」だけ | 完走者の記録を巻き込んで下げないため |
| 雑魚まんじゅうの意味を裏返す | 0問の人の中に、事故の被害者が区別できない形で混ざっているため |
| アーカイブの成績もポイントに入れる | 総合ランキングは「WA検定でどれだけ遊んだか」の総合点だから。<br>当初はポイント外にしていたが、方針を変更した（2026-09-01）。 |
| アーカイブの1日上限は廃止（2026-09-11） | 251問→50問→廃止と二転三転した末、<br>「初挑戦の問題だけ加点」に置き換えて上限そのものを外した。<br>`dailyPointCap: 0` で上限なし。数字を入れれば復活する（仕組みは残してある） |
| MiAuthの権限を read:account に | トークンを一度も使っていなかった。投稿権限は不要だった |

## 既知の弱点（未解決）

1. **1問ごとの記録になっていない** … 途中離脱の記録が消える。最優先
2. **本人確認がない** … localStorage を書き換えれば誰にでもなりすませる。
   オーナー判定も同じ方式なので、オーナー画面にも入れる
3. **点数の自己申告** … WA王の正解数はブラウザが数えた値をそのまま保存している。
   照合で検出はできるが、防止はできていない
4. **他人の挑戦枠を潰せる** … 他人名義のエントリーを作れてしまう

1〜4はすべて、**サーバー役を持てば解決する**。

## 2026-09-11：配点の全体設計をやり直した

### きっかけ
1日で **1340pt** 稼ぐ人が出た。アーカイブの問題を251問×3〜4周していた。

### 診断（実際に計算した）
現状の配点は、狙いと正反対のことを報酬していた。

| 事実 | 意味 |
|---|---|
| 30日皆勤のログイン = **65pt** | 目標1位の行動が、最も報われていない |
| アーカイブ50問を1日やると **80pt** | **1日の周回が、1か月皆勤を上回る** |
| 普段のクイズ5問 = 8pt ≒ 作問0.8問 | 10分の作問と、1分の5問がほぼ同価値 |
| 1日に入る上限が実質なし（理論上1598pt/日） | 周回が常に最適解になる |

根本原因は **「クイズを解く」が1問2ptで、1日の上限が無いこと**。
ログインは月に30回しか発生しないが、クイズは無限に積める。

### 一律上限では解決しなかった
1日20問に絞っても、30日で960pt。周回する人が1位のままだった。
1日10問まで下げて、ようやく「交流する人 > 周回する人」の順序になった。
しかしそれでは普通に遊ぶ人まで窮屈になる。

### 採用した解：初挑戦・初正解の1回だけ加点
- **クイズを解く**（1pt）… その問題を**はじめて解いたとき**の1回だけ
- **正解ボーナス**（1pt）… その問題に**はじめて正解したとき**の1回だけ（何回目の挑戦でもよい）
- 2回目以降は何度解いても0

これで **1日の上限そのものが不要**になった。未挑戦の問題がある限り何問でも入る。

**周回する人の伸び方（6か月・月20問ずつ問題が増える想定）**

    467 → 564 → 661 → 758 → 855 → 952

1か月目で全問解き終わるので、以降は新作ぶんしか増えない。
3か月後には「作問する人」に抜かれ、下位に落ちる。
一方で交流する人は 735 → 1424 → 1951 → … と伸び続ける。

**正解ボーナスを「初回の解答」ではなく「はじめて正解したとき」にした理由**：
間違えた問題をあとから解き直して覚える行為を報いたいため。
1問につき最大1回なので、繰り返しても増えない。

### ログインボーナスを厚くした
「休まないこと」に意味が無かったため。

| | 30日皆勤 | 5日に1回休む | 差 |
|---|---|---|---|
| 変更前 | 65pt | 54pt | **11pt** |
| 変更後 | 125pt | 54pt | **71pt** |

5日ごとのボーナスを +5 → **+10**、**30日達成 +30** を新設。
アクティブな人の点数に占めるログインの割合が 11.6% → 20.1% になった。

### 既存ポイントは凍結した
配点を変えると、毎回全件から計算し直す作りのせいで過去も変わってしまう。
そこで **2026-09-11 の終わり（9/12 0時）で締めて `legacy_points` に保存**し、
以降だけを新ルールで計算する形にした。

`legacy_points` がまだ無い間は、これまでどおりの計算に自動でフォールバックする。
SQLを実行するまでの間も表示が壊れない。

## 2026-09-11：ポイント獲得の吹き出し

押した場所から「＋1pt」がふわっと浮かんで消える（note のあれ）。
リアクション・コメント・作問・クイズの解答に対応。

**嘘の数字を出さないために、クイズは自分の解答履歴を先に読んでから表示する。**
初挑戦で正解なら＋2pt、初挑戦で不正解なら＋1pt、
解いたことのある問題に初めて正解したら＋1pt、2回目以降は表示なし。

OSの「視差効果を減らす」がオンの人には、フェードだけの控えめな表示に切り替わる。

## 2026-09-11：リアクションを絵文字式にした

- ♥と🤣の固定2種類をやめ、**好きな絵文字を選ぶ方式**に（AERU/Misskey と同じ感覚）
- **1つの投稿につき1人1つ**。同じものをもう一度押すと外れる
- **コメントにもリアクション**を追加（`comment_reactions` テーブル）。押す1pt / 付けられる3pt
- 面白クイズランキングを廃止し、**種類を問わないリアクションランキング**に置き換え

**既存の kind（'funny' / 'heart'）はデータベースの値を変えていない。**
表示のときだけ🤣と❤️に読み替えている。
理由：締め日の集計SQLが `kind = 'funny'` で絞っているため、
値を書き換えると凍結ぶんの計算と食い違う。
