# WA API の使いどころ（検討メモ）

WA運営から Member App 用の仕様（OAuth 2.0 + PKCE の SSO ＋ REST API ＋ SDK）が公開された。
WA検定にとって何が使えるかを整理する。

---

## 先に結論：SSO はセキュリティ問題の直接の解にはならない

期待していたのは「SSOのトークンを Supabase に検証させて RLS で守る」だったが、
**仕様にJWTやJWKSの記載がなく、`/me` に問い合わせて確かめる形式**に見える。
Supabase の RLS はデータベースの中で完結するので、外部APIへ問い合わせられない。

つまり **本人確認をするには、結局サーバー役（Edge Function）が要る**。
ただしその Edge Function が本人確認する相手として、
**Misskey より WA の方が適している**：

- WAのユーザーIDは整数で安定している（Misskeyのハンドルは表示名変更の影響を受けにくいが、サーバー移転に弱い）
- `roles` が取れるので、オーナー判定を「らちのハンドル決め打ち」から卒業できる
- WAにログインしていない人は入れない＝コミュニティ外の人を最初から排除できる

→ **Plan B は「Edge Function ＋ WA SSO」で組むのがよい。**

## 使えるもの（優先度順）

### 1. `profile:read` — ログインをWA SSOに寄せる　★最優先
`wa.user.me()` で id / name / avatar_url / roles が取れる。

- いまの MiAuth ログインを置き換えられる
- **アイコン問題が消える**。いまは Misskey の `users/show` を1人ずつ叩いて
  端末に7日キャッシュしているが、その仕組みが要らなくなる
- Plan B の土台になる

注意：public client のトークンは **60分**で切れる。SDKが自動更新するが、
**WAからログアウトするとアプリからもログアウトされる**。

### 2. `notifications:write` — 通知　★効果が大きい
**運営審査あり**。既定はオフで、アプリ側に受信設定の画面を用意する必要がある。

- 「本日の問題が出ました」
- 「あなたの作った問題にコメントが付きました」
- 「WA王決定戦、締切まであと3時間」

いま新着コメントはアプリを開かないと気づけない。**継続率に直結する。**
予約配信（`scheduled_at`）があるので、締切リマインドが作れる。

制限：送り先は**常に利用者本人**。他のメンバーには送れない。
配信待ちは50件まで。書き込みは 30リクエスト/時/ユーザー。

### 3. `tv_schedules:read` / `streams:read` — 作問の材料　★中級編と直結
中級編の定義は「複数のメンバーが関わり、**アーカイブや配信で後から見返せる**こと」。
番組表と配信アーカイブは、**その定義そのものの供給源**。

やれること：
- 作問画面で「この配信から1問つくる」を選べるようにし、
  タイトル・日付・アーカイブURLを問題の出典として添える
- 問題の解説に配信へのリンクを自動で入れる（`link_url` が既にある）

**作問のハードルが下がる**のが効く。251問が増えていくかどうかはここ次第。

### 4. `posts:write` — シェアをアプリ内で完結
いまは `/share` のURLを別タブで開いている。`wa.posts.create({ text })` なら
アプリを離れずに投稿できる。

注意：利用者がAERU未連携だと `409 POSTS_BACKEND_UNAVAILABLE`。
そのときは今の方式（`/share` を開く）に落とす作りにしておく。

### 5. `notes:read` / `notes:write` — コラム
- 結果発表をコラムに残す（アプリ内の順位は流れていくが、コラムなら記録になる）
- 投稿には **Pro / Active プラン**が必要。らちのプラン次第

## 使わないもの

| Scope | 理由 |
|---|---|
| `profile:write` | 表示名を変える機能はWA検定に無い |
| `events:read/write` | イベント機能は持たない |
| `products:*` | 商品紹介は関係ない |
| `posts:read` | 投稿1件の取得は使い道が無い（タイムライン一括取得は提供されていない） |
| `tv_schedules:write` | 番組表に書き込む理由が無い |

**最小権限にする**こと。使わないScopeを足さない。

---

## 設計上の制約（重要）

仕様の禁止事項に **「取得したデータを保存・再配布する設計にしないこと」** とある。

→ **WAから取ったデータ（配信情報・コラム・プロフィール）を Supabase に
コピーして貯めてはいけない。** 表示のたびに取りに行く作りにする。
いまやっている「Misskeyのアイコンを `profiles` に書き戻す」に相当することを、
WA API のデータでやってはいけない。

レート制限：60回/分/ユーザー、1000回/時/アプリ。
一覧画面で1人ずつプロフィールを引くような作りにしない。

## 進め方の案

| 段階 | 内容 |
|---|---|
| 0 | `wa-app.json` を配置し、My Apps で登録 → `client_id` を取得（**ステータスを「公開中」に**） |
| 1 | `profile:read` だけでログインをWA SSOに置き換える。まず動かす |
| 2 | Edge Function を立て、SSOトークンを `/me` で検証してから読み書きさせる（＝Plan B） |
| 3 | 通知（運営審査を申請）、番組表からの作問支援 |

段階1と2の間で、**MiAuthとWA SSOのどちらでもログインできる期間**を設けると安全。
いきなり切り替えると、WAアカウントとMisskeyアカウントの対応が取れていない人が
締め出される。既存データのユーザー識別子は Misskey のハンドルなので、
**移行時に「WAのユーザーID ↔ Misskeyハンドル」の対応表が要る**。
（`profiles` テーブルに wa_user_id 列を足して、初回ログイン時に紐づける）
